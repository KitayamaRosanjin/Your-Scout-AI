## 1. プロジェクト概要 & 技術選定理由

### **Q. なぜこの構成にしたのですか？**

| 要素 | 採用技術 | 選定理由・アピールポイント |
| :--- | :--- | :--- |
| **言語** | **Python 3.14** | **「最新技術への適応力」をアピールするため**です。通常、業務では安定版（3.11/3.12）が使われますが、あえて最新版を採用し、未知の環境構築に対応できる基礎力を示しています。 |
| **インフラ** | **AWS CDK** (Python) | **「Infrastructure as Code (IaC)」の実践**です。GUIの手動操作（ポチポチ）は再現性がなく、Git管理もできません。コードでインフラを管理することで、チーム開発やCI/CDへの理解を示しています。また、Terraformではなく言語統一（Python）ができるCDKを選びました。 |
| **実行基盤** | **AWS Lambda (Container/Docker)** | **「Python 3.14を動かすため」の技術的解決策**です。AWS Lambdaの標準機能（Zipアップロード）はPython 3.14に未対応です。そこで、Dockerコンテナに自分たちでPython 3.14環境を構築してデプロイする「コンテナイメージLambda」の手法を採用しました。 |

## 2. 開発ステップ（時系列）と使用コマンド

これまでの作業を時系列順に解説します。

### **Step 1: プロジェクトの土台作成**
まず、プロジェクトを管理するディレクトリ構造を作り、AWS CDKのプロジェクトを初期化しました。

*   **コマンド**:
    *   `mkdir portfolio-saas`: フォルダ作成
    *   `cdk init app --language python`: CDKプロジェクトの自動生成を行うコマンド。これでAWS推奨のディレクトリ構成が一発で作られます。

### **Step 2: Python 3.14実行環境の構築 (Docker)**
LambdaでPython 3.14を動かすための「コンテナ」を定義しました。

*   **作成ファイル**: `app/Dockerfile`
*   **内容**: `FROM python:3.14-slim` と記述し、公式のPython 3.14イメージをベースに採用。ここに依存ライブラリ (`requirements.txt`) とアプリコード (`collector.py` 等) をコピーする指示を書きました。

### **Step 3: インフラ定義 (CDK Coding)**
PythonコードでAWSのリソースを定義しました。

*   **編集ファイル**: `cdk_app/cdk_app_stack.py`
*   **定義したリソース**:
    1.  **DynamoDB**: 求人データを保存するデータベース。
    2.  **Lambda**: 上記のDockerイメージを使って動く関数（収集・判定・通知）。
    3.  **EventBridge**: 定期実行（Cron）のためのタイマー。

### **Step 4: 検証 (Synth)**
記述したインフラ定義が正しいAWS CloudFormationテンプレートに変換できるか検証しました。

*   **コマンド**: `cdk synth` (Synthesizeの略。構成ファイル生成コマンド)

## 3. 実装フェーズ（Phase 2: Coding Core Logic）

インフラの準備が整った後、実際のアプリケーションロジック（Pythonコード）を機能ごとに実装しました。

### **機能1: 求人収集 (Collector)**
*   **ファイル**: `app/collector.py`
*   **役割**: RSSフィードから求人情報を取得し、DynamoDBに保存する。
*   **工夫した点（面接アピール）**:
    *   **重複排除**: 毎回同じ求人を通知しないよう、DynamoDBの `ConditionExpression='attribute_not_exists(job_id)'` を使用して、**「まだDBに存在しない場合のみ保存する」**というロジックを実装しました。これにより、無駄な処理コストを削減しています。

### **機能2: マッチングエンジン (Matcher)**
*   **ファイル**: `app/matcher.py`
*   **役割**: 新着求人が保存されたことを検知し、LLM（今回はモック）を使って「自分に合っているか」を判定する。
*   **工夫した点（面接アピール）**:
    *   **イベント駆動アーキテクチャ**: 定期実行ではなく、**DynamoDB Streams** をトリガーにしました。「DBにデータが入ったら即座にLambdaが動く」というリアルタイムな仕組みです。
    *   **LLM連携の設計**: 求人のタイトル・詳細文と、自分のレジュメを比較してスコアリングする関数 `analyze_job_match` を設計しました。

### **機能3: 通知機能 (Notifier)**
*   **ファイル**: `app/notifier.py`
*   **役割**: スコアが高い「勝てる求人」だけをDiscord/Slackに通知する。
*   **工夫した点（面接アピール）**:
    *   **フィルターの実装**: 全ての判定結果を通知するのではなく、ステータスが `MATCHED` に変わった瞬間だけを検知するようにストリームを制御しました。これにより通知ノイズを減らしています。

### **開発プロセス: ローカルテスト戦略**
クラウド（AWS）にデプロイする前に、ローカル環境で動作確認を行いました。
*   **Why?**: デプロイして確認→修正のサイクルは時間がかかるため。
*   **How?**: 各ファイルの `if __name__ == "__main__":` ブロックに、**「モック（偽物）のデータ」**を使って関数を動かすテストコードを書きました。これにより、AWS環境がなくてもロジックの正しさを手元で検証できました。

## 4. 面接で話せる「トラブルシューティング」体験

開発中に3つのエラーに遭遇し、それぞれ特定・解決しました。これらは**「問題解決能力」のエピソード**として非常に有効です。

### **Bug 1: 依存関係インストールの失敗**
*   **事象**: `pip install -r requirements.txt` を実行したら、「pipコマンドが見つからない」というエラーが出た。
*   **原因**: Windows環境特有のパス設定の問題で、直接 `pip` が呼べなかった。
*   **解決策**: `python -m pip ...` というコマンドを使用。これは「Python本体経由でpipモジュールを呼び出す」という、環境に左右されにくい確実な方法です。

### **Bug 2: CDKのAPI仕様誤認**
*   **事象**: `cdk synth` を実行したら、Pythonのエラー（`TypeError`）で落ちた。
    *   エラー内容: `DockerImageFunction got an unexpected keyword argument 'cmd'`
*   **原因**: Lambda関数の定義で、実行コマンドを指定する `cmd` 引数を書く場所を間違えていた。関数の直下ではなく、イメージ定義 (`DockerImageCode`) の中で指定する必要があった。
*   **解決策**: 公式ドキュメント（あるいはエラーメッセージ）に基づき、コードの構造を修正した。

### **Bug 3: 型（Type）の不一致**
*   **事象**: 再度 `cdk synth` をしたら、また別のエラーが出た。
    *   エラー内容: `TypeError: argument item must be str`
*   **原因**: DynamoDBストリームのフィルター設定で、`['INSERT']` (リスト) と書いていたが、正しくは `'INSERT'` (文字列) でなければならなかった。
*   **解決策**: エラーが出ている箇所を一時的にコメントアウトして特定し（切り分け）、リストから文字列に修正した。

### **Bug 4: モジュール未検出 (ModuleNotFoundError)**
*   **事象**: ローカルで `collector.py` を実行したら `ModuleNotFoundError: No module named 'boto3'` が出た。
*   **原因**: コンテナ用の `requirements.txt` は定義していたが、ローカル環境にはインストールしていなかった。
*   **解決策**: `pip install -r app/requirements.txt` を実行し、開発環境にも依存ライブラリを入れた。

## 5. 今後の展望（面接での返し）
「この後はどうするつもりだったの？」と聞かれたらこう答えます。

*   **デプロイ**: `cdk deploy` コマンドだけで、この構成すべてをAWS上に展開できる状態になっている。
*   **AI実装**: `matcher.py` のロジック部分を `openai.ChatCompletion.create` に置き換えれば、本物のAIマッチングが動き出す。
*   **スケーラビリティ**: 現在は無料枠内（DynamoDB, Lambda）だが、アクセスが増えればキャッシュ（ElastiCache）や非同期処理（SQS）を導入してスケーラビリティを高める設計にする。
